# 连续全双工变声：当前边界与下一步

GPT-Live-1 的持续音频和本项目现有按句转换是两种不同的生命周期。原生 Echo 接入不能直接证明“Echo → 角色声音”的全双工已经可用。

## 已确认的代码约束

- `prefix_quality.py` 的 runner 限制单次输入为 480000 个16kHz样本，即30秒；内容特征与随机噪声缓存会随该次输入增长。简单删掉时限会引入内存和计算量增长。
- 当前 `gemini_bridge.py` 使用 Gemini 的 `turnComplete` 做重采样收尾和 `/v1/flush`；GPT-Live 的主音频流没有该事件，不能自行捏造等价的“说完一句”。
- 当前变声配置需要32个BN帧（1280ms）额外上下文；分块声码器还使用32个mel帧（320ms）未来上下文。这些参数不是整条通话的端到端延迟。
- GPT-Live 可以返回16kHz PCM；它可按sidecar格式送入转换器，不能再误按24kHz的Gemini音频进行重采样。
- 浏览器在GPT原声模式继续上传麦克风和静音，不执行Gemini模式的本地RMS自动打断。模型让话与丢弃本机已排队声音是不同的行为。

因此当前只开放有凭据时可启动的 `gpt_live_native`，不注册或伪装 `gpt_live_vc`。现有Gemini转换保持原实现。

## 有API权限后的验收顺序

1. **Echo原声**：记录解析后的`session.started`模型、voice、采样率；收到非零音频。输出期间持续发送输入，人工确认模型听见中途新增内容；退出取得`session.closed`。协议mock测试不能代替此步。
2. **相同输入的变声比较**：保存同一次Echo输出，使用同一角色参考，分别做整段转换和现有流式转换。先用30秒以内片段，直接比较原声、角色参考和两路结果；不能用不同模型、台词的样本归因。
3. **持续状态方案**：在隔离分支验证60秒及以上输入，明确如何限制BN/noise缓存、保留上下文和安全切换状态；测峰值内存、积压、输出连续性。不要为赶工在讲话中随意flush并冒称等价。
4. **取消与过期输出**：给播放器和转换队列加明确的generation/epoch策略，验证旧输出不会进入下一段；不存在的上游turn/interrupt事件不能作为同步依据。
5. **接入视频**：取得实际通话worker接口后，把同一条转换音频送往播放和嘴型驱动，再验证同步。当前仓库不包含该视频服务。

## 记录方式

每次记录要分开保存“模型首次输出”“转换首次输出”“浏览器安排播放”与重叠输入窗口。人工听感、音色相似度和是否能边听边说分别验收；不能凭文件生成、低延迟或自动评分宣称全部通过。
